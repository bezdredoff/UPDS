# Match-3 Human Playtest Protocol v1

Канонический повторяемый human playtest для UPDS Match-3.

## Цель

Процедура нужна для сравнимых human samples после изменений Match-3. Она дополняет, но не заменяет:

- deterministic CI baseline;
- Browser Gate;
- Mobile WebKit Golden Samples;
- локальную telemetry и Match-3 Playtest Summary в `?qa=1 → Диагностика`.

Главное правило: между сравниваемыми билдами меняется продукт, а не метод тестирования.

## Когда использовать

Использовать после изменений, которые могут повлиять на понятность, причинность, темп, topology, blockers, story objects, hints, specials или subjective fun.

Для чисто технических refactor без player-facing эффекта достаточно automated gates.

## Среда

1. Открыть тестируемый билд с `?qa=1`.
2. Для formal sample предпочтителен текущий stable Pages build. Candidate/preview допустим, если тестируется конкретный PR; обязательно записать BUILD из Diagnostics.
3. Играть на реальном целевом portrait device, если он доступен. Если тест проводится на desktop, это явно отмечается в session notes.
4. Язык игры фиксируется на всю сессию.
5. Использовать **Level Lab**, потому что он запускает production `LevelDefinition` + production `Match3Game`, не меняет Story progress и пишет exact seed в telemetry.

## Перед тестом

В `?qa=1 → Диагностика`:

1. записать VERSION и BUILD;
2. если текущая telemetry нужна — сначала нажать `Экспорт playtest report` и сохранить JSON;
3. нажать `Очистить playtest data`;
4. убедиться, что Match-3 Playtest Summary показывает empty state;
5. открыть Level Lab.

`Очистить playtest data` не является сбросом игрового save. Story/Campaign progress специально не очищается.

### Seed contract

Основной comparative run каждого уровня использует **seed `120000`**.

- Если найден воспроизводимый visual/gameplay defect — сразу сделать `Retry same seed` и записать, воспроизвёлся ли он.
- Если есть подозрение, что субъективная проблема вызвана конкретной раскладкой, после основного cohort можно сделать follow-up на **seed `120004`** и пометить его как follow-up, а не как часть основной выборки.
- Нельзя менять seed посреди основной восьмёрки только потому, что попытка кажется «неудачной».

## Поведение тестера

Тестер играет естественно.

- Не просить специально использовать или не использовать Hint.
- Не подсказывать authored move, objective route, special combo или правильную стратегию.
- Не объяснять значение blocker/story-object до того, как игрок сам взаимодействует с системой.
- Если тестер просит помощь, дать минимально необходимый ответ и записать intervention в notes.
- Не превращать сессию в обучение механикам: непонимание само является данными.

После каждого уровня сразу заполнить пять оценок по шкале 1–5 и короткую заметку.

## Пять обязательных оценок

Одинаковые вопросы задаются после каждого уровня.

1. **Понятность цели** — я понимал, что нужно сделать.
2. **Визуальная читаемость** — tiles, blockers, story objects и состояние поля различались без лишнего усилия.
3. **Причинность** — я понимал, почему после моего действия поле изменилось именно так.
4. **Осмысленный выбор** — у меня были решения, а не ощущение случайного перебора доступных ходов.
5. **Fun / желание продолжать** — мне хотелось сделать ещё ход или перейти к следующему уровню.

Якоря шкалы:

- `1` — явно плохо / непонятно / неприятно;
- `3` — смешанное или нейтральное ощущение;
- `5` — явно хорошо / понятно / хочется продолжать.

Не нужно объяснять тестеру, какой score считается «правильным».

## Что записывать кроме score

После каждого уровня:

- outcome: win / loss / abandon;
- использовался ли manual Hint;
- был ли auto Hint заметен;
- была ли помощь facilitator;
- один самый непонятный момент, если он был;
- один лучший момент, если он был;
- defect/repro note при технической проблеме.

Не нужно вручную считать moves, cascades, invalid moves или duration — это уже делает telemetry.

## Завершение сессии

После восьми основных уровней:

1. вернуться в `?qa=1 → Диагностика`;
2. проверить, что Match-3 Playtest Summary содержит сыгранные уровни;
3. нажать `Экспорт playtest report`;
4. сохранить/переименовать JSON так, чтобы рядом можно было хранить subjective session notes;
5. заполнить финальные вопросы из шаблона.

Рекомендуемое имя notes:

`UPDS_M3_playtest_<date>_<tester-id>_<build>.md`

Рекомендуемое имя telemetry export после скачивания:

`UPDS_M3_playtest_<date>_<tester-id>_<build>.json`

Tester ID должен быть псевдонимом/номером, а не обязательным реальным именем.

## Финальные вопросы

1. Какой уровень был самым интересным и почему?
2. Какой уровень был самым слабым и почему?
3. В какой момент было больше всего непонимания?
4. Где возник самый сильный payoff / приятный момент?
5. Хотелось бы после этой восьмёрки продолжить играть ещё 10 минут? `да / нет / не уверен`
6. Если изменить только одну вещь в Match-3, что это должно быть?

## Как интерпретировать sample

Human data не является автоматическим balance gate.

- `N=1` полезен для defects, грубых UX проблем и гипотез; он не доказывает общий win-rate/fun verdict.
- Одинаковая конкретная проблема у **2+ независимых testers** — достаточная причина открыть investigation item.
- При **N>=5** median `<=3` по одной и той же обязательной оценке — сильный сигнал для следующего design pass.
- Нельзя тюнить moves/objectives только потому, что один tester проиграл конкретный seed.
- Telemetry сравнивается только между сессиями с одной версией protocol и понятным BUILD.
- Если subjective feedback и telemetry расходятся, сохраняются оба сигнала; один не «отменяет» другой.

## Change decision

После изменения повторяется тот же cohort и тот же основной seed `120000`.

Изменение считается подтверждённым human evidence, если оно решает исходную повторяющуюся проблему без появления новой повторяющейся проблемы в соседней категории. Маленькая sample не требует статистической значимости; решение фиксируется как directional evidence, а не как доказанный population effect.

## Stop conditions

Сессию можно остановить раньше восьми уровней, если:

- build имеет blocker/crash, делающий дальнейшие результаты бессмысленными;
- tester явно устал и оценки становятся нерепрезентативными;
- устройство/браузер начал системно ломать input/rendering.

Причина остановки обязательно записывается. Неполная сессия не смешивается с полной как будто это одинаковый cohort.
